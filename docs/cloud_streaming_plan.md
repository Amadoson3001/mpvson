# Mpvson cloud streaming implementation plan

Reviewed checkout `68754ce`. This document is the implementation handoff for Windows and Linux. The findings below come from tracing the code and checking the engine and protocol documentation. Runtime playback, network timings, and fallback engine behavior still need the fixture runs in Phase 0. The local Flutter launcher stopped before tests because it could not find Git in its executable search path.

## Target behavior

Paste an HTTP(S) media URL and play it promptly. The player should seek when the source supports seeking, recover from short network interruptions, and offer the resolutions the source actually provides. `Auto` starts conservatively and adjusts when the current engine and source have a verified quality-switching path. A manual selection stays in effect for the current queue entry. The app reports the selected mode and the actual decoded resolution independently.

| Source | First release behavior |
| --- | --- |
| Direct HTTP(S) video or audio, including signed URLs and redirects | Stream through libmpv. Seek if supported. Display the source resolution when known. |
| HLS master and media playlists | Play VOD and live. Offer manual quality and Auto on masters with a verified variant mapping. Play single-rendition media playlists directly. Preserve associated audio and subtitles. |
| Clear DASH MPD | Use the original MPD. Offer manual video representations on verified engines with a reliable track mapping. Enable Auto only where a switch passes the network and continuity tests. Unmapped MPDs use the engine default. |
| Supported public video pages | Resolve through a managed `yt-dlp` integration. Prefer direct playable formats and support synchronized video and audio inputs. Publish provider support only after testing it. |
| Cloud share pages and restricted sources | Direct media links follow the first row. Add a share-page adapter only for a verified provider and public share type. Give a specific message for a login, expired link, DRM, or unsupported page when the cause is known. |

The first release focuses on clear HTTP(S) media played on demand. Use libmpv for media fetching and decoding, and Dart for bounded metadata discovery, selection, and recovery. Exercise local files, UNC shares, and URL-saving consent during regression testing.

## Ownership and contracts

Keep the open dialog, startup and forwarded CLI opens, file or URL drop where supported by the OS, Linux MPRIS `OpenUri`, queue, recent, and restore paths on their existing route into `PlayerController`. Centralize validation at ingress and begin network work only for the selected entry. Enqueue and session restore can finish without I/O to media origins. Use the existing open behavior preference and distinguish request acceptance from eventual playback success. [Startup wiring](../lib/main.dart#L390), [desktop integration](../lib/data/services/desktop_integration_service_impl.dart#L780), [controller staging](../lib/ui/player/player_controller_engine.dart#L214)

| Owner | Data and behavior |
| --- | --- |
| Queue and session | Existing entry ID, exact original URL, title, progress and consent. Use the original source for queue, history and resume. Preserve query contents, case and ordering in transport requests. |
| Streaming coordinator in the playback data layer | Active request ID, linked engine attempt, cancellation and deadline. Own classification, bounded discovery, the in-memory resolved source, current quality policy, retry and quality-switch decisions. Inject HTTP, process, time and engine seams for tests. |
| Native adapter | Selected input and optional audio input, source-scoped options, native playlist entry ID and lifecycle, typed failures when available, actual video and cache state. Copy any FFI payload before the callback returns. |
| Player controller and UI | User intent, queue navigation and progress, a small observable stream state for status and quality, actions for retry or quality selection. Keep per-position updates on existing timeline listeners. |

Use two identities. The logical queue entry and original URL survive quality changes, redirects and URL refresh. Each native load or reopen has its own attempt ID. The controller accepts only events from the active attempt and commits progress only after its load is attached. Keep temporary endpoints, headers, expiry hints, and native track or edition IDs in memory. Suggested types are `ResolvedStream`, `StreamRendition`, and `StreamPlaybackState`. Follow the existing state ownership map. [State ownership](player_state_ownership.md)

## Phase 0 — Measure the current engines

1. Use the Flutter version pinned by desktop CI and record OS, engine version, FFmpeg version, and Windows DLL flavor. Test the bundled Windows engine in an installed and portable build, the Windows fallback engine supported by the app, and the distro libmpv used by Linux packaging. Record unsupported properties as capabilities rather than guessing from the version number. [Windows engine provenance](../packaging/windows/engine-provenance.json), [desktop workflow](../.github/workflows/desktop.yml)
2. Build a deterministic local HTTP fixture server with a request ledger and bandwidth shaping. Use tiny generated media with visible rendition markers and an audio marker. Start with fast-start range-capable MP4, redirected extensionless MP4, HLS with two renditions and separate audio/subtitles, and clear DASH. Add a rolling live playlist and disconnected/stalled routes. Make fixture generation reproducible and keep normal Flutter tests independent of the system FFmpeg executable.
3. Record URL-to-load and URL-to-first-output separately, seek recovery, native lifecycle order, request URLs and ranges, active rendition, and peak cache usage. For video, measure rendered output or a render-frame counter. For audio-only, use playback restart with advancing media time. Record at least the direct, HLS, and local-file baselines. Treat `FILE_LOADED` as headers ready and keep it distinct from first output. [libmpv event API](https://github.com/mpv-player/mpv/blob/v0.42.0/include/mpv/client.h)
4. Test `edition-list`, `current-edition`, and `hls-bitrate` on HLS, and `track-list` plus native video track selection on DASH. On each successful switch, check requested segments and decoded resolution together. Test audio/subtitle continuity and live position. Record whether the backend flushes, seeks, or reopens on switching. The bundled mpv explicitly maps HLS programs to editions, and changing `edition` can restart playback. [mpv editions](https://mpv.io/manual/stable/#command-interface-edition), [mpv v0.42.0 selection code](https://github.com/mpv-player/mpv/blob/v0.42.0/demux/demux_lavf.c#L997), [FFmpeg DASH demuxer](https://ffmpeg.org/doxygen/8.1/dashdec_8c.html)

**Acceptance.** Commit the fixture and a compact engine capability and results table. Expose each control only where the backend passes its fixture. Exercise direct playback on every engine in the release matrix.

## Phase 1 — Reliable direct opens and cancellation

1. Reuse `MediaSource.validate` in all ingress paths, retaining local file and folder handling. Add one deduplication key with Windows case folding applied only to local paths. Keep request URLs as entered apart from surrounding whitespace and the fragment that HTTP omits. Exercise raw request targets through both Dart and the final native client with mixed-case tokens, `%2F`, repeated query keys, optional `+`, and redirect locations. Fix normalization only where a test demonstrates a change. Use the existing `MediaEntry` identity behavior for local paths and verify compatibility with stored remote history if its comparison key changes.
2. Give direct media an immediate engine path, including unknown extensions. Use the URL path for preliminary media-kind hints and update them from the actual tracks. Let the engine discover seekability. A valid `206` and `Content-Range` establish that a specific byte range was honored. A missing `Accept-Ranges` is inconclusive. Starting at the engine avoids duplicate `HEAD` or Range probes that can consume limited-use links. [HTTP Range semantics](https://www.rfc-editor.org/rfc/rfc9110.html#section-14)
3. Add typed native `START_FILE`, `FILE_LOADED` and `END_FILE` events in the existing vendored media_kit event loop. Keep EOF observation for the `keep-open` behavior and use the native end reason to distinguish errors, stops, redirects, and actual completion. In the single-item open path, bind the appended engine playlist entry ID to the app attempt before setting `playlist-pos`, and pair `FILE_LOADED` with the ordered start. Map supported engine playlist redirects by their native IDs or reject unrecognized playlist expansion explicitly. HTTP redirects and resolver results inherit the current attempt. Treat property-only fallback on an engine without the typed path as a conservative compatibility mode. [Vendored open path](../packages/media_kit/lib/src/player/native/player/real.dart#L151), [vendored event loop](../packages/media_kit/lib/src/player/native/player/real.dart#L1494), [libmpv event API](https://github.com/mpv-player/mpv/blob/v0.42.0/include/mpv/client.h)
4. Make resolution and engine dispatch cancelable. Issue an attempt synchronously, then resolve outside `_openTail`. Serialize native mutations only. A new selection, stop, clear queue, removal of the active item, timeout, and shutdown revoke the attempt, cancel network work, and stop the old engine load when appropriate. Check ownership after every await and before writing engine options or publishing. A revoked attempt cannot later attach even if its original URL matches the selection. Release the open-request coordinator after a streaming request has been accepted so the next request can supersede it. Leave append and local playback behavior covered by existing regressions.
5. Use typed stages for resolving, connecting, buffering, ready, reconnecting, switching quality, and failed. Keep a cache stall visible when the controller adopts loaded media. A paused open can reach ready once tracks attach. Measure actual first output independently. Stop and failure clear the spinner, cancel preview work, and leave the selected row retryable. Play and pause during an open update the intent the winning attempt applies. Coalesce or cancel stale seeks. Mark completion only on verified media EOF, with a separate policy for an ended live stream. Guard `prepareCurrentPaused` so restored remote rows stay idle until the user requests playback. [Paused restore](../lib/ui/player/player_controller_transport.dart#L40)

**Acceptance.** Direct, redirected, signed, slow and non-range streams behave correctly. Test slow A followed by B, A reopened while A is loading, playback stopped during load, and late EOF or error. Only the active attempt can produce audio or update history and progress.

## Phase 2 — Buffering, retries and smart fetching

1. Introduce one owner for per-load native streaming settings. Apply them in the same serialized lane as opening or use file-local options with tested availability. Keep normal local, UNC, progressive HTTP(S), adaptive VOD, and live profiles distinct where the measurements justify it. Verify that settings, request headers, auxiliary audio and resume options reset on network-to-local transitions. Preserve existing renderer and memory preferences.
2. Start testing with memory-backed network buffering, about 12 seconds of progressive or VOD readahead and 6 seconds for ordinary live HLS. Try 0.75–1.5 seconds of refill buffering and initial prebuffering only where it improves first output and first-minute stalls. Set supported I/O timeouts for main and nested network reads within the attempt deadline. Honor `demuxerCacheLimits`, keep native bytes and seconds independently bounded, and test peak RSS. Enable disk cache only if measurements justify it, with cleanup and an observed disk budget. Tune these starting values against Phase 0 results. [mpv cache options](https://mpv.io/manual/stable/#cache), [mpv network options](https://mpv.io/manual/stable/#network)
3. Keep the engine in charge of segment and Range fetching. Account for backend-native retry behavior, including Windows curl and HLS segment retries, in a single end-to-end budget. Start with 25 seconds from direct open to ready and 35 seconds for a page URL. Cap whole-source transient reopen attempts at two within the remaining budget, with 0.5 and 1.5-second delays plus bounded jitter. Honor a valid `Retry-After` within the budget. Apply the same caps to a single reconnect episode after startup. Reset the episode only after sustained healthy playback. Retry timeouts, disconnects, 408, 429, and selected 5xx when positively identified. Treat missing media, ordinary 401/403, invalid TLS, and unsupported formats as terminal. Unknown engine failures get a generic safe message, with the manual Retry action. Return a fresh URL at most once for a resolver-owned expiring link with verified expiry or authorization failure. Reuse the original source and captured position for seekable VOD. Use the latest available point for live, keeping DVR position only when still valid.
4. Sample active network throughput, buffered duration, cache pauses and decoded size at low frequency while they are needed. Use `paused-for-cache` to distinguish underruns from user pause. Treat `raw-input-rate` as an estimate in bytes per second and use it when the demuxer is actively filling cache and a seek has settled. Normalize to bits per second for comparisons. Derive estimates from active playback requests and fetch queued items on selection. [mpv cache properties](https://mpv.io/manual/stable/#command-interface-demuxer-cache-state)
5. Gate remote seek previews on a healthy, seekable source and deliberate hover. Reuse safe discovery metadata, and prefer explicit thumbnails or a verified low-cost preview input. Disable remote preview for authenticated, live, or otherwise unbounded sources until supported. Cancel its HTTP and native work on buffering, seek, quality switch, source change, or stop. Enforce one remote preview operation and retain the frame LRU. Delete the preview-specific duplicate manifest fetch when the shared discovery path provides the same result. [Seek preview service](../lib/data/services/seek_preview_service.dart#L1269)

**Acceptance.** A fixture with a bounded interruption resumes the same item at the same queue index. Failure beyond budget stops network activity and gives a usable Retry action. Local performance, memory mode, and disk usage pass the Phase 0 comparison.

## Phase 3 — HLS, DASH and stream quality

1. Share the HLS parsing logic with main playback while keeping the preview policy independent. Discover a known manifest with a bounded GET when justified for initial selection. Use native discovery first for extensionless or known limited-use URLs. Fall back promptly to native playback on metadata failure. Start with a discovery cap of two seconds, five redirects, 256 KiB HLS or 512 KiB MPD of decoded body, and 128 advertised candidates. Validate the final redirect and resolve references against its URL. Honor HLS attribute quoting, distinguish master from media playlists, retain rendition groups, and offer full video variants in the video menu. Preserve each child URL's query as advertised and apply parent query inheritance only where defined by the protocol or a verified provider. Use a bounded DASH XML parser with external entity expansion disabled and recognize unsupported DRM where possible. Expire discovery for live and short-lived endpoints promptly. [HLS specification](https://www.rfc-editor.org/rfc/rfc8216.html#section-4.3.4), [DASH-IF interoperability guidance](https://dashif.org/guidelines/iop-v5/)
2. **HLS.** Keep the master URL as the playback input whenever the engine offers a verified program selection. On the bundled engine start with a file-local `hls-bitrate` ceiling and use `edition-list` metadata and `current-edition` for mapping/confirmation. Match discovered candidates by native metadata, using dimensions and codec when available. Hide ambiguous mappings, including duplicate bandwidth values that cannot be distinguished. Use explicit edition selection or a controlled reopen on VOD if the fixture proves that path. On older engines, a direct child URL is a fallback only for independently playable muxed variants, after proving it retains required behavior. A child must never silently drop associated audio, captions, or subtitles. [mpv HLS option](https://mpv.io/manual/stable/#options-hls-bitrate), [mpv editions](https://mpv.io/manual/stable/#command-interface-edition), [HLS rendition rules](https://www.rfc-editor.org/rfc/rfc8216.html#section-4.3.4.2.1)
3. **DASH.** Keep the original MPD and let libmpv/FFmpeg resolve periods, initialization, and media segments. Map only demonstrably equivalent video representations in the active video adaptation set to native tracks. Switch via the native video track API when fixture logs and output verify the mapping. Keep audio and subtitle selections independent. For live, multi-period, or unmappable MPDs, retain native playback and show only the quality capabilities established by the fixture. Required support is clear adaptive VOD playback on the tested engine matrix, with manual selection on tested configurations. If a backend cannot select reliably, report the limitation with actual engine evidence in the handoff. [Native video track API](../packages/media_kit/lib/src/player/native/player/real.dart#L1001), [FFmpeg DASH demuxer](https://ffmpeg.org/doxygen/8.1/dashdec_8c.html)
4. **Manual.** Offer `Auto` plus the confirmed input choices. Distinguish same-height options only when bitrate, codec, or frame rate helps. Use `Source` or the actual resolution as information for a fixed rendition. A switch keeps the same queue item and preserves VOD position, current rate, volume, latest pause/play intent, and stable audio/subtitle choices when available. Match language, role and codec across reopened tracks. Restore the selected video track when the player returns from a hidden view, after verifying that the track belongs to the active attempt. Commit the new state after native confirmation and confirm resolution once frames arrive. If the switch fails, restore the last working rendition once and explain the result. For live, offer switching only after verifying DVR or live-edge behavior.
5. **Auto.** Start at a compatible rendition near 720p or below within an initial 2 Mb/s total bitrate budget when the source offers one, and choose the lowest compatible option if none fits. For unknown metadata use a verified conservative engine default. Use a short moving estimate based on real fetching. Start testing downshifts after persistent buffer depletion or two underruns in 30 seconds, and upshift one rung only after at least 30 seconds of healthy buffer and sustained throughput at least 1.5× the next rendition's total bitrate. Use a cooldown and bound the number of automatic reopen-based switches. Suspend the policy during seeks, pause, manual locks and recovery. Enable upshifts only when the verified switch cost meets the playback targets. A backend that can only do an initial choice or outage recovery should say so in playback info. Report observed behavior as adaptive, restart-based, or fixed based on the fixture evidence.

**Acceptance.** Selecting 360p and 720p changes both the requested media and rendered resolution. Separate HLS audio and subtitle fixtures still work. Under bandwidth loss Auto converges to a sustainable rendition. A failed or canceled change preserves queue identity and the last confirmed progress.

## Phase 4 — Public page resolution and delivery

1. Add an injectable `yt-dlp` resolver for known supported public page URLs and verified HTML fallback cases. Use metadata-only mode with `--ignore-config`, `--no-playlist`, `--no-download`, `--dump-single-json`, and `--` before the validated URL. Use a fixed executable path and an argument list with `runInShell: false`. Use `ProcessRunner.start` or extend that seam with bounded stdout and stderr and real cancellation. Its existing `run` timeout only ends the wait. Kill and reap the helper and its managed children on timeout or cancellation. Reject collection results and unsupported protocols. [Process runner](../lib/data/services/process_runner.dart#L59), [yt-dlp options](https://github.com/yt-dlp/yt-dlp#usage-and-options)
2. Parse only the needed JSON fields and filter compatible formats first. Prefer a viable muxed rendition when it meets the selected quality and codec requirements. For higher-quality separate inputs, load video and audio with source-scoped options or the verified native external audio path, and confirm both streams before reporting readiness. Keep the same audio across video switches when its timing and compatibility are verified. Filter external URLs and headers, reject embedded newlines, and keep secrets origin-scoped. An authenticated format that cannot be safely scoped across redirects or auxiliary inputs needs a clear unsupported/authentication result. Verify that the app resolver and native ytdl hook cannot resolve the same item twice. [mpv external audio](https://mpv.io/manual/stable/#options-audio-files), [vendored header hook](../packages/media_kit/lib/src/player/native/player/real.dart#L2152)
3. Re-resolve the original page when an expiring CDN URL needs refresh. Keep generated CDN or manifest URLs, cookies, per-rendition headers, and helper output exclusively in memory. Memoize successful resolution only in bounded session memory and before confirmed expiry. Cover fresh playback and resume from a saved original page with a fake expiring URL and fixture request logs.
4. Start with a pinned, checksum-verified upstream Windows helper for installer and portable builds, and a documented installed helper on Linux. Check licenses and notices alongside the binary, use absolute allowlisted executable paths, and avoid downloads triggered by pasted URLs. For providers requiring EJS and a JavaScript runtime, include a tested pinned runtime path on packaged Windows and documented Linux requirements before advertising support. Add a helper status to troubleshooting. Verify installed, portable, and missing or outdated helper behavior. Keep extractor delivery independent of the libmpv engine updater. [yt-dlp dependencies](https://github.com/yt-dlp/yt-dlp#dependencies), [yt-dlp EJS guide](https://github.com/yt-dlp/yt-dlp/wiki/EJS), [release workflow](../.github/workflows/release.yml), [Windows installer](../packaging/windows/installer.iss)

**Acceptance.** A deterministic fake resolver exercises muxed and split audio/video, cancellation, expiration, and helper failure. Smoke-test each advertised provider with an authorized public fixture outside required CI. Missing helper or unsupported page has a specific message and leaves direct URLs playable.
